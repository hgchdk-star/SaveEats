## 0. 프로젝트 컨텍스트

SaveEats는 대학 캡스톤/졸업작품으로 시작하는 모바일 서비스 프로젝트다.

현재 팀 구성은 다음과 같다.

| 담당 | 역할 |
|---|---|
| 서정 | 서비스 기획, UX/UI, 디자인 시스템, 브랜딩, 기획 변경 관리 |
| 지우 | React Native 프론트엔드 구현 |
| 혜지 | 백엔드/DB 영역, Supabase 중심 구현 |

협업에는 Git/GitHub를 사용하며, 디자인 및 개발 보조 도구로 Claude Design/Claude Code를 활용한다.

본 문서는 팀원 모두가 같은 제품을 만들기 위한 **제품 기준점(SSOT)** 이다. AI 도구를 사용하더라도 본 문서에 없는 제품 정책을 임의로 추가하거나, 이미 확정된 정책을 다른 의미로 재해석하지 않는다.

### 0.1 졸업작품과 실제 서비스의 관계

SaveEats는 졸업작품 규모로 MVP를 구현하지만, 향후 **실제 서비스 운영과 수익화 가능성**을 고려한다.

의사결정 기준:
1. 현재 팀과 일정 안에서 MVP로 구현 가능한가.
2. 실제 서비스로 확장할 때 핵심 구조를 폐기하지 않아도 되는가.
3. 운영·수익화 단계에서 데이터·정책·외부 연동 구조가 발목을 잡지 않는가.

> **MVP에서 구현하지 않는다 ≠ 설계에서 고려하지 않는다.**

MVP는 작게 만들되, 주문·리뷰·상태 이력·이미지·분석 이벤트·외부 연동은 향후 확장이 가능하도록 책임과 데이터를 분리한다.

# 1. 서비스 개요

## 1.1 서비스명

**SaveEats**

## 1.2 한 줄 정의

> **배달음식을 주문하듯 메뉴를 고르고, 음식 대신 그 주문금액을 내 계좌로
> 보내는 대안 배달 경험**

## 1.3 한 문장으로 보는 핵심 UX

> **사용자는 음식을 주문하듯 메뉴를 고르고 주문한다. 다만 음식 대신
> 주문금액이 자신의 계좌로 배달된다.**

## 1.4 핵심 아이디어

SaveEats는 사용자가 배달음식을 먹고 싶어지는 순간, 일반적인 배달앱처럼
가게와 메뉴를 탐색하고 옵션을 고르고 장바구니에 담도록 한다.

일반 배달앱의 흐름은 다음과 같다.

**가게 탐색 → 메뉴 선택 → 장바구니 → 주문 → 음식 배달 완료**

SaveEats는 이 익숙한 행동 구조를 최대한 유지하되 마지막 결과만 바꾼다.

**가게 탐색 → 메뉴 선택 → 장바구니 → 주문 → 주문금액이 내 계좌로 배달
완료**

즉 SaveEats의 핵심은 단순히 "돈을 저축하는 기능"이 아니다.\
사용자가 배달을 고민하는 바로 그 순간의 행동과 감정을, 익숙한 음식 주문
경험 안에서 다른 결과로 연결하는 것이 제품의 본질이다.

------------------------------------------------------------------------

# 2. 문제 정의

배달앱은 사용자가 먹고 싶은 음식을 빠르게 찾고 주문할 수 있도록 매우
편리하게 설계되어 있다. 반면 배달을 시킬지 고민하는 순간에 "이번에는
주문하지 않고 그 금액을 남겨두고 싶다"고 생각하더라도, 그 행동을
자연스럽게 이어주는 경험은 부족하다.

기존 저축·가계부·핀테크 서비스는 사용자가 이미 소비를 하지 않기로 결정한
뒤 돈을 관리하는 데는 적합하지만, **음식을 고르고 주문하고 싶은 바로 그
순간의 욕구와 행동 흐름**을 직접 다루지는 않는다.

SaveEats는 이 지점에서 출발한다.

사용자가 배달앱을 켜듯 SaveEats를 열고, 실제로 먹고 싶은 메뉴를 고르고,
가격까지 확인하고, 장바구니와 주문 과정을 거친 뒤 그 주문금액을 자신의
계좌로 보내도록 한다.

따라서 SaveEats가 해결하려는 문제는 단순한 "저축 부족"이 아니라 다음과
같다.

-   배달을 고민하는 순간에 사용할 수 있는 대체 행동 경험이 부족하다.
-   절약 행동은 음식 주문만큼 직관적이고 재미있게 설계되어 있지 않다.
-   단순히 "참았다", "돈을 아꼈다"는 기록만으로는 다시 서비스를 사용할
    동기가 약하다.
-   기존 금융 UI를 전면에 내세우면 배달을 고민하던 사용자의 감정과
    맥락이 끊긴다.

# 3. 제품 목표와 비목표

## 3.1 제품 목표

SaveEats는 다음 경험을 만드는 것을 목표로 한다.

1.  배달을 고민하는 순간 자연스럽게 앱을 열 수 있어야 한다.
2.  실제 배달앱처럼 메뉴를 탐색하는 재미가 있어야 한다.
3.  메뉴를 선택하고 장바구니에 담는 과정까지 음식 주문의 익숙한 문법을
    유지해야 한다.
4.  최종 단계에서는 실제 음식 주문이 아니라는 사실을 명확히 알려 오해를
    방지해야 한다.
5.  주문금액을 자신의 계좌로 보내는 행동을 "내 계좌로 배달"되는 경험으로
    느끼게 해야 한다.
6.  완료된 주문이 내역으로 쌓여 사용자가 자연스럽게 누적 결과와 성취감을
    확인할 수 있어야 한다.
7.  다른 사용자의 활동은 SNS가 아니라 배달앱 리뷰와 주문 지표처럼
    자연스럽게 보여야 한다.
8.  사용자가 음식에 죄책감을 느끼거나 다이어트/금식 앱을 사용하는 것처럼
    느끼지 않게 해야 한다.

## 3.2 비목표

SaveEats는 다음 서비스가 되는 것을 목표로 하지 않는다.

-   다이어트 앱
-   금식/식단 억제 앱
-   음식을 먹는 행위에 죄책감을 주는 앱
-   "N일 연속 참기"를 핵심으로 하는 습관 앱
-   일반적인 가계부
-   투자/자산관리 서비스
-   목표 금액 달성률이 전면에 나오는 적금 앱
-   SNS 게시글과 팔로우가 중심인 커뮤니티
-   실제 음식점에 음식 주문을 전달하는 배달 주문 중개 서비스

# 4. 가장 중요한 제품 원칙

> **"저축 앱에 음식 UI를 입히는 것이 아니라, 배달앱인데 돈의 목적지만
> 바뀐다."**

이 원칙은 SaveEats의 홈, 검색, 가게 상세, 메뉴, 장바구니, 주문, 완료,
내역, 리뷰까지 모든 화면의 판단 기준이다.

사용자가 메뉴를 탐색하는 동안 `저축`, `절약`, `참기`, `모으기`를
반복적으로 노출하지 않는다.\
그 구간의 주인공은 **음식, 가게, 메뉴, 가격, 옵션, 리뷰**다.

금융적 의미는 필요한 순간에만 명확하게 드러낸다.

특히 최종 주문 확인에서는 실제 음식이 주문되지 않고 주문금액이 등록한
계좌로 이동한다는 사실을 반드시 분명하게 안내한다.

# 5. 핵심 타깃과 사용 상황

## 5.1 핵심 사용자

SaveEats의 핵심 사용자는 배달음식을 주문할지 말지 고민하는 순간이
있으며, 때로는 그 소비를 하지 않고 해당 금액을 남겨두고 싶어 하는
사용자다.

제품은 사용자를 "절제력이 부족한 사람", "과소비하는 사람", "다이어트가
필요한 사람"으로 규정하지 않는다.

## 5.2 핵심 사용 순간

대표적인 사용 순간은 다음과 같다.

-   야식이 먹고 싶어 배달앱을 켜고 싶은 순간
-   특정 치킨, 피자, 디저트 등 메뉴가 강하게 당기는 순간
-   이번 달 배달을 많이 시켰다고 느껴 한 번 정도는 주문하지 않으려는
    순간
-   실제로 주문했을 경우 얼마를 썼을지 구체적인 메뉴와 가격을 보면서
    결정하고 싶은 순간
-   이전에 SaveEats로 보냈던 금액과 주문 내역을 확인하고 싶은 순간
-   같은 메뉴를 고민했던 다른 사람의 SaveEats 리뷰를 보고 싶은 순간

# 7. 카피 및 용어 원칙

## 7.1 `참기`는 핵심 기능명이 아니다

기존에 검토했던 다음 표현은 기본 UX에서 사용하지 않는다.

-   참기 후기
-   참기 성공
-   참기 기록
-   참은 금액
-   N일 연속 참기

`참기`는 행동을 직관적으로 설명할 수 있지만, 음식 섭취를 억압하거나
죄책감을 유발하고 다이어트/금식 앱처럼 보일 위험이 있다.

SaveEats는 사용자의 행동을 "음식을 참았다"고 규정하지 않는다.

## 7.2 `패스`, `다른 선택`도 최소화

`패스`와 `다른 선택`은 서비스 철학이나 캠페인성 문구에서 제한적으로
사용할 수 있으나, 메인 기능명이나 반복 CTA로 사용하지 않는다.

## 7.3 기본 권장 언어

-   주문
-   메뉴
-   장바구니
-   주문금액
-   계좌
-   배달
-   내역
-   기록
-   SaveEats 리뷰
-   땡김도

## 7.4 금융 관련 `등록`과 `연결`

용어를 구분한다.

-   사용자가 계좌 정보를 입력하거나 송금 목적지를 설정하는 행위:
    **등록**
-   실제 금융 API나 금융기관과 기술적으로 연동되는 행위: **연결**

실제로 API 연동되지 않은 기능을 `계좌 연결`이라고 표현해 금융 연동이
완료된 것처럼 오인시키지 않는다.

## 7.5 보조 브랜드 카피

브랜드 설명이나 캠페인 영역에서는 다음과 같은 방향을 사용할 수 있다.

> **음식은 오지 않지만, 돈은 도착합니다.**

단, 실제 주문 과정에서는 감성 카피보다 사용자가 결과를 정확히 이해할 수
있는 명확한 문구를 우선한다.

# 8. 정보 구조

## 8.1 Bottom Navigation

**홈 / 검색 / 찜 / 내역 / 마이**

- 홈: 음식 탐색 및 추천
- 검색: 가게·메뉴·카테고리 검색
- 찜: 사용자가 저장한 **가게**
- 내역: SaveEats 주문 기록, 상태 확인, 주문 이어하기, 리뷰 작성 진입
- 마이: 프로필, 계좌, 개인 기록, 내가 쓴 리뷰, 배지, 설정

`통계`는 별도 Bottom Navigation 탭으로 두지 않는다. `커뮤니티`도 별도 탭으로 만들지 않는다.

## 8.2 찜 범위

MVP의 찜 대상은 **Store only**다. 메뉴 찜은 제공하지 않는다.

# 9. 전체 핵심 사용자 플로우

## 9.1 최초 진입

**첫 실행 → 최초 1회 온보딩(건너뛰기 가능) → 홈**

온보딩에서는 로그인이나 계좌 등록을 강제하지 않는다.

## 9.2 탐색부터 주문까지

**홈/검색/카테고리 탐색 → 가게 선택 → 메뉴/옵션 선택 → 장바구니 → 주문금액 확인 → `주문하기`**

게스트도 여기까지 탐색하고 장바구니를 사용할 수 있다.

## 9.3 개인 행동 시 인증

찜, 계좌 등록, 주문 진행, 내역, 리뷰, 마이 등 사용자 개인 데이터가 필요한 행동에서 인증을 요구한다. 로그인 성공 후 원래 행동/화면으로 복귀하고, 로그인 실패/취소 시 게스트 Cart는 유지한다.

## 9.4 주문 완료 플로우

`주문하기` → 계좌 미등록 시 계좌 등록 → 최종 주문 확인 → 실제 음식 미주문 및 주문금액 이동 고지 → **`[○○원 내 계좌로 주문하기]`** → Order를 `PENDING`으로 먼저 생성 → 토스 주문 이어가기 또는 직접 주문 이어가기 → SaveEats 복귀 → `주문을 완료하셨나요?` → 사용자 완료 확인 시 `USER_CONFIRMED` → **`○○원이 내 계좌로 배달됐어요`** → 내역/리뷰/개인 기록.

핵심 루프는 **음식 탐색 → 주문 경험 → 계좌 배달 → 기록 → 리뷰/사회적 증거 → 재방문**이다.

# 17. 찜

# 18. 장바구니

메인 CTA는 **`주문하기`**.

게스트 Cart 허용, 로컬 임시 저장, 로그인 중/실패/취소 시 유지, 로그인 성공 시 사용자 Cart로 승격. 복잡한 merge는 만들지 않고 충돌 시 최신 로컬 Cart 우선.

**Single-Store Cart**. 다른 Store 메뉴를 담으려 하면 기존 Cart가 비워진다는 확인을 제공. **One Order = One Store**.

가격 변경은 조용히 갱신하지 않고 변경 전/후를 명시하고 확인 후 주문 가능. 품절 항목/옵션은 해결 전까지 주문 CTA 비활성화.

# 20. 송금 및 외부 금융앱 연동

MVP는 정식 BaaS/오픈뱅킹을 전제로 하지 않는다. 1차 편의 경로는 **토스 URL Scheme을 이용한 주문 이어가기**이며, 계좌/은행/금액 사전입력은 Android/iOS 최신 실기기 PoC를 통과한 경우에만 활성화한다.

> **딥링크는 편의 기능이지 SaveEats 주문의 핵심 보장 수단이 아니다.**

사용자 용어: `토스로 주문 이어가기`, `다른 방법으로 주문하기`, `직접 주문 이어가기`, `계좌번호 복사`, `금액 복사`, `주문 완료가 필요해요`, `주문 이어하기`, `주문 완료`, `주문 취소`.

직접 주문 이어가기에서는 계좌번호와 금액을 **별도로, 사용자 동작으로만** 복사하고 `[토스 열기]`를 제공한다. 자동 Clipboard 금지.

`tossDeepLinkEnabled` Remote Kill Switch를 둔다. OFF면 안전한 직접 주문 이어가기 흐름으로 전환한다.

향후 공식 금융 API/BaaS/오픈뱅킹 등으로 자동 검증과 `VERIFIED` 도입 가능. Order를 Toss에 종속시키지 않는다.

# 21. SaveEats 주문/거래 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | 주문 시작 후 완료 확인 필요 |
| `USER_CONFIRMED` | 사용자가 완료를 확인했지만 자동 검증은 못한 상태 |
| `VERIFIED` | 향후 공식 연동으로 시스템 검증한 상태 |
| `FAILED` | 검증 가능한 과정에서 실패 확인 |
| `CANCELLED` | 사용자 명시 취소 |

SaveEats 복귀 후 **주문을 완료하셨나요?** → `[아직이에요] [주문 완료했어요]`.

완료 시 `USER_CONFIRMED`, `completedAt`. `아직이에요`는 `PENDING` 유지이며 실패/취소가 아니다. 내역에서 **주문 완료가 필요해요 / 주문 이어하기** 제공. PENDING 자동 만료는 미정.

상태 저장 실패 시 **송금을 이미 완료했다면 다시 송금하지 마세요.**를 안내하고 동일 Order ID의 상태 저장만 재시도한다.

# 24. 주문 상태 업데이트 빨간 점

빨간 점은 **미확인 주문 상태 업데이트** 의미이며 리뷰 미작성과 무관하다.

해당 OrderHistoryItem + Bottom Navigation `내역`에 표시. 행이 화면에 **50% 이상 약 1초** 노출되면 read. 화면 체류 중 새 업데이트도 먼저 unread 생성 후 같은 조건으로 read.

읽음 저장 실패는 사용자에게 오류를 띄우지 않고 UI에서는 읽음 처리 후 **silent retry**.

OrderStatusUpdate는 읽었다고 삭제하지 않고 `orderId`, `fromStatus`, `toStatus`, `createdAt`, `viewedAt/read` 등 이력을 보존한다.

# 25. SaveEats 리뷰 --- 기본 개념

기존의 `참기 후기`는 폐기하고 **SaveEats 리뷰**를 사용한다.

리뷰는 SNS 게시글이 아니라 **일반 배달앱 리뷰 UI**에 가깝게 설계한다.

## 25.1 목적

리뷰는 다음 경험을 공유하기 위한 기능이다.

-   해당 메뉴가 얼마나 먹고 싶었는지
-   어떤 메뉴를 골랐는지
-   얼마의 주문금액을 내 계좌로 보냈는지
-   짧은 이유나 감정
-   같은 메뉴를 고민하는 다른 사용자가 가볍게 참고할 수 있는 경험

## 25.2 땡김도

실제로 음식을 먹지 않았으므로 맛 별점을 사용하지 않는다.

**땡김도 ★ 1\~5**

예:

**땡김도 4.8 ★★★★★**\
**SaveEats 리뷰 1,284**

`맛있어요`, `양이 많아요`, `배달이 빨라요`, `조리가 잘 됐어요` 등 실제로
음식을 먹거나 배달받았다는 전제가 필요한 평가 항목은 사용하지 않는다.

------------------------------------------------------------------------

# 26. 리뷰 범위와 진입점

리뷰 화면의 제목은 항상 **`SaveEats 리뷰`**다.

`가게 전체 리뷰`, `뿌링클 리뷰`처럼 제목을 바꾸어 범위를 설명하지
않는다.

범위는 사용자가 어디에서 진입했는지에 따라 데이터 쿼리로 결정한다.

-   가게 상세 → `storeId` 기준 → 해당 가게의 여러 메뉴에 대한 리뷰 전체
-   메뉴 상세 → `menuId` 기준 → 해당 메뉴의 리뷰만

동일한 Review UI를 사용하고, 실제 범위는 진입점/쿼리에서 결정한다.

------------------------------------------------------------------------

# 27. ReviewSummary 및 정렬/필터

정렬: **최신순(기본) / 리뷰 도움순 / 별점 높은 순 / 별점 낮은 순**. 향후 데이터가 충분하면 `추천순` 추가 가능.

사진은 MVP **최대 1장**, 데이터 구조는 Review 1 : ReviewImage N 확장 가능하게 한다.

------------------------------------------------------------------------

# 28. ReviewCard

기본 순서: 작성자 표시명 → 땡김도/작성일 → 메뉴명 → 사진(선택) → 본문 → `27,000원 · 주문 완료` → 도움돼요.

MVP 작성자는 실명 마스킹, 향후 공개 닉네임 가능.

도움돼요: 로그인 필요, 사용자당 리뷰당 1회, toggle 취소 가능, 자기 리뷰 불가, `ReviewHelpful(userId, reviewId)` unique 권장.

Validation: 땡김도 필수 / 본문 **5~500자** / 사진 선택 최대 1장.

SaveEats 리뷰는 기본 **공개 리뷰**. 공개/비공개 선택은 MVP 미제공.

신고는 설계 포함, MVP **SHOULD**.

------------------------------------------------------------------------

# 29. 마이 > 내가 쓴 리뷰

기본 정렬은 **`createdAt DESC`**. 오래된 리뷰를 수정했다고 최상단으로 올리지 않는다.

가게명, 땡김도/작성일, 메뉴, 사진, 본문, 주문금액/완료 정보, 받은 도움돼요, 수정됨, 수정/삭제를 제공. 리뷰가 많아지면 무한스크롤. Empty State: **아직 작성한 SaveEats 리뷰가 없어요.**

# 30. 리뷰 작성 가능 기간

리뷰는 **주문 완료 후 30일 동안** 작성할 수 있다.

내부 계산은 날짜 단위가 아니라 주문 완료 timestamp를 기준으로 한다.

`reviewDeadline = completedAt + 30 days`

즉 정확히 **30 × 24시간**이다.

예:

9월 1일 오후 3시 주문 완료\
→ 10월 1일 오후 3시까지 작성 가능\
→ 해당 시각을 초과하면 작성 기간 만료

사용자에게는 기술적으로 표현하지 않고 다음처럼 안내한다.

> **리뷰는 주문 완료 후 30일 동안 작성할 수 있어요.**

## 30.1 리뷰 상태 규칙

### Case A --- 리뷰 없음 + 30일 이내

`리뷰 쓰기`

### Case B --- 리뷰 존재

`✓ 리뷰 작성 완료 · 보기`

이미 작성한 리뷰는 30일이 지나더라도 조회·수정·삭제할 수 있다.

### Case C --- 기존 리뷰 삭제 + 아직 30일 이내

다시 `리뷰 쓰기`

삭제 후 재작성 가능.

### Case D --- 기존 리뷰 삭제 + 30일 초과

`리뷰 작성 기간이 지났어요`

재작성 불가.

### Case E --- 처음부터 리뷰 미작성 + 30일 초과

`리뷰 작성 기간이 지났어요`

## 30.2 핵심 원칙

> **한 주문에는 동시에 하나의 활성 리뷰만 존재할 수 있으며, 주문 완료 후
> 30일 이내라면 리뷰를 삭제한 뒤 새 리뷰를 다시 작성할 수 있다.**

"한 주문당 평생 한 번만 리뷰 작성 가능" 정책은 사용하지 않는다.

------------------------------------------------------------------------

# 31. 리뷰 수정·삭제·재작성

수정 가능: 땡김도 / 본문 / 사진. 수정 불가: Order / Store / Menu / 주문금액 / 작성자. 수정은 같은 Review record이므로 도움돼요 유지.

삭제는 **soft delete(`deletedAt`)** 기본. 30일 초과 리뷰 삭제 전 **삭제하면 이 주문에는 리뷰를 다시 작성할 수 없어요.** 경고.

삭제 후 `completedAt + 30×24h` 이내면 새 Review 작성 가능, 도움돼요 0부터 시작. 한 Order에는 동시에 하나의 active Review만 존재. `completedAt` 없는 비정상 Order는 리뷰 대상 아님.

------------------------------------------------------------------------

# 32. 리뷰의 사장님 답글

MVP에서는 실제 사장님 답글 기능을 제공하지 않는다.

향후 AI가 "사장님처럼" 답변하는 기능을 검토하더라도 실제 점주가 작성한
답글처럼 위장해서는 안 된다.

LATER 기능으로 도입한다면 예를 들어 다음처럼 AI임을 명확히 표시한다.

-   `AI 사장님 · AI`
-   `SaveEats AI 답글`

실제 사장님과의 제휴/입점 구조가 없는 상태에서 실재 점주의 답글인 것처럼
표현하지 않는다.

------------------------------------------------------------------------

# 33. 다른 사용자의 활동과 사회적 증거

SNS 피드를 핵심 기능으로 만들지 않는다. 리뷰 수, 땡김도, 실제 집계된 활동 지표처럼 음식 탐색에 자연스럽게 녹인다. Seed 단계에서 실제 사용자가 존재하는 것처럼 보이는 주문 수를 임의 생성하지 않는다.

## 33.1 LATER — 다른 사용자의 공개 리뷰 모아보기
향후 ReviewCard 작성자 닉네임을 누르면 그 사용자의 **공개 SaveEats 리뷰 목록**을 볼 수 있게 할 수 있다. 팔로우/팔로워, DM, SNS 게시물/피드는 핵심 범위 밖.

------------------------------------------------------------------------

# 34. 통계와 개인 기록

금융 자산관리 대시보드가 아니라 SaveEats 사용 기록을 가볍게 보여준다.

예: **9월의 SaveEats** — 주문 8회 / 내 계좌로 배달된 금액 184,500원 / 가장 많이 고른 음식 치킨 / 가장 큰 주문 42,000원.

월간 기록은 이전 달 탐색 가능, 미래 월 이동 불가. 월 경계 KST.

캘린더는 **SHOULD**. SaveEats 주문이 있었던 날을 표시하며 streak/참기 성공 캘린더로 만들지 않는다.

------------------------------------------------------------------------

# 35. 목표 기능

목표저축은 핵심 기능이 아니다.

목표 기능을 전면에 두면 SaveEats가 배달앱이 아니라 적금·재테크 앱처럼
보일 위험이 있다.

따라서 목적별 계좌, 여행 목표, 새 노트북 목표, 진행률 등은 **LATER 또는
선택적 부가기능**으로 둔다.

사용자가 목표 기능을 사용하지 않아도 핵심 SaveEats 경험은 완전하게
작동해야 한다.

------------------------------------------------------------------------

# 36. 배지와 게이미피케이션 — SHOULD

음식 억제 자체를 보상하지 않는다. 후보: 첫 주문 / 10번째 주문 / 10만원 도착 / 50만원 도착 / 치킨 단골.

배지는 현재 유효한 Order 데이터 기준으로 조건 재계산 가능한 구조를 권장한다.

------------------------------------------------------------------------

# 37. 마이페이지

구조: 프로필/계정, 돈이 배달될 계좌, 이번 달 요약, 누적 기록, 내가 쓴 리뷰, 배지(SHOULD), 알림 설정, 설정.

신규 사용자: **아직 SaveEats 주문이 없어요 / 메뉴 둘러보기** Zero State.

한 섹션 실패로 전체를 막지 않고 실패 섹션만 재시도. MVP 프로필은 계정 정보 중심, 공개 영역은 마스킹 이름, 향후 공개 닉네임 가능.

------------------------------------------------------------------------

# 38. 알림 — SHOULD

알림함과 Push Notification은 **SHOULD**. 주문 상태/완료, 작성 가능한 리뷰, 월간 기록, 서비스 필수 안내, 향후 혜택/추천을 설계상 구분한다. 장기적으로 유형별 ON/OFF. 주문 중요 알림과 마케팅 알림은 분리한다. 죄책감/압박성 문구 금지. 리뷰 알림과 내역 unread는 별개.

------------------------------------------------------------------------

# 39. 음식·가게 데이터 전략

MVP는 **Seed/Demo Data**. `Store → Menu → MenuOption` 일반화 구조로 특정 예시 가게에 하드코딩하지 않는다.

향후 정식 데이터 Source/입점/제휴로 교체할 수 있게 한다. 실제 업체명, 상표, 로고, 메뉴 이미지, 음식 사진, 가격 데이터의 상업적 사용권은 상용화 전에 별도 검토한다.

# 42. 디자인 및 브랜드 방향

## 42.1 가장 중요한 시각 원칙

> **배달앱스러움이 먼저 느껴져야 한다.**

-   음식 사진 비중을 높인다.
-   가게/메뉴 카드가 중심이 된다.
-   가격을 명확하게 보여준다.
-   카테고리 탐색을 친숙하게 만든다.
-   하단 고정 CTA와 장바구니/주문 패턴을 적극 활용한다.
-   리뷰 중심 정보 구조를 사용한다.
-   숫자, 잔액, 차트가 화면을 지배하지 않게 한다.
-   특정 기존 배달앱을 그대로 복제하지 않는다.

참고 대상으로 배달의민족, 쿠팡이츠, 요기요, 땡겨요의 익숙한 배달앱
문법을 살피되 화면 구성과 브랜드를 직접 카피하지 않는다.

## 42.2 최종 Primary

**Tomato `#F0523D`**

이 컬러는 SaveEats의 음식 탐색과 주문 행동을 대표하는 핵심 브랜드
컬러다.

## 42.3 Tomato 역할 분리

현재 Design System의 확정 역할:

-   Brand Primary / 큰 주문 CTA: `#F0523D`
-   작은 filled control 등 흰 글자 대비가 더 필요한 영역: `#D93D29`
-   선택된 Bottom Navigation 텍스트 등 더 진한 Tomato 텍스트: `#B5301F`

흰색과의 대비는 각각 약:

-   `#F0523D`: 3.51:1
-   `#D93D29`: 4.52:1
-   `#B5301F`: 6.16:1

큰 주문 CTA는 `#F0523D`를 유지하되 현재 디자인 시스템에서는 큰/굵은
텍스트를 사용한다.

## 42.4 Semantic Color

브랜드 Tomato와 상태 색상의 역할을 섞지 않는다.

-   **Tomato:** 음식 탐색, 주문, 주요 브랜드 액션
-   **Green:** 실제 계좌 이동 성공/완료 상태
-   **Yellow:** 땡김도, 보상/성취 포인트
-   **Warm Cream / White / Charcoal:** 기본 배경 및 중립 정보

오류 상태의 red와 브랜드 Tomato 역시 의미를 구분한다.

## 42.5 Tomato의 의미

`Tomato`는 컬러 이름이다.

브랜드 전체를 토마토 과일 캐릭터, 토마토 일러스트, 토마토 이모지로
도배하지 않는다.

음식 사진이 항상 화면의 주인공이어야 한다.

## 42.6 기존 컬러 검토에서 폐기된 방향

-   Blue/Green 중심: 핀테크/토스 인상이 강해 배달앱 느낌이 약함
-   Purple 중심: 배달/음식과의 연결감이 약함
-   Orange 단독 중심: 주요 배달앱 컬러와의 구분을 추가 검토해야 했음

최종적으로 Tomato `#F0523D`를 Primary로 확정했다.

**먹고 싶은 메뉴가 떠오름**\

# 50. 현재 확정된 핵심 결정사항

1. SaveEats는 **저축앱보다 배달앱 경험을 우선**한다.
2. 핵심 원칙은 **배달앱인데 돈의 목적지만 바뀐다**이다.
3. 최초 1회 **3페이지 온보딩 MUST**, Skip 허용, 로그인/계좌등록 강제 없음.
4. 게스트는 탐색과 Cart 사용 가능. 개인 행동에서 로그인한다.
5. MVP 인증은 이메일+비밀번호를 기본으로 한다.
6. Bottom Navigation은 **홈 / 검색 / 찜 / 내역 / 마이**.
7. 찜은 **Store only**.
8. 검색 대상은 Store/Menu/Category, 결과 UI는 StoreCard only.
9. 메뉴 검색 매치 시 StoreCard에서 매칭 메뉴를 보여주고 SaveEats 리뷰 수를 표시한다.
10. FoodCategoryChip은 single-select.
11. Menu 수량은 1~10.
12. Cart는 Single-Store, One Order = One Store.
13. 가격 변경/품절은 사용자 확인/해결 전 주문 불가.
14. 계좌 미등록이어도 탐색/Cart 가능, 주문 시 등록 후 원래 흐름 복귀.
15. MVP 계좌는 1개이며 변경/삭제 가능, 과거 Order에는 계좌 Snapshot 유지.
16. 장바구니 CTA는 `주문하기`, 최종 CTA는 `○○원 내 계좌로 주문하기`.
17. 최종 CTA에서 외부앱 이동 전에 `PENDING` Order를 먼저 생성한다.
18. Toss URL Scheme은 실기기 PoC 통과 시 편의 경로로 사용하며 공식 송금 API로 간주하지 않는다.
19. `직접 주문 이어가기`를 항상 대체 경로로 제공하고 계좌번호/금액은 별도 사용자 복사.
20. `tossDeepLinkEnabled` Kill Switch를 둔다.
21. SaveEats 복귀 후 사용자 완료 확인 시 `USER_CONFIRMED`, 자동 검증 없이는 `VERIFIED` 금지.
22. `아직이에요`는 PENDING 유지, PENDING 자동 만료는 미정.
23. 상태 저장 실패는 송금 실패가 아니며 재송금을 자동 유도하지 않는다.
24. 내역은 최신순+무한스크롤, 부분 로딩 실패 시 기존 데이터 유지.
25. 같은 메뉴 보기는 현재 Menu가 유효할 때만 제공.
26. unread는 Order row 50% 이상 약 1초 노출 시 read.
27. read 저장 실패는 silent retry, OrderStatusUpdate 이력은 유지.
28. 리뷰는 **SaveEats 리뷰**, 평가는 **땡김도**.
29. 리뷰 기본 정렬은 최신순.
30. 리뷰 본문은 5~500자, 땡김도 필수, 공개 리뷰.
31. 리뷰 사진은 MVP 최대 1장, 데이터 구조는 다중 이미지 확장 가능.
32. 리뷰 신고는 SHOULD.
33. 도움돼요는 로그인 사용자당 리뷰당 1회 toggle, 자기 리뷰 불가.
34. 리뷰 수정은 도움돼요 유지, 삭제는 soft delete.
35. 리뷰 작성 기한은 `completedAt + 30×24h`, 삭제 후 기한 내 재작성 시 새 Review/도움돼요 0.
36. 향후 공개 닉네임 + 다른 사용자의 공개 리뷰 모아보기는 LATER, SNS 팔로우/DM은 핵심 범위 밖.
37. 통계는 금융 대시보드가 아니라 SaveEats 기록 중심.
38. 캘린더/배지/알림함/Push는 SHOULD.
39. MVP 음식/가게 데이터는 Seed/Demo Data, 실제 집계처럼 보이는 가짜 사용자 수는 표시하지 않는다.
40. DB timestamp는 UTC, 사용자 표시/정책과 월 경계는 KST.
41. Order/Menu/Option/Account Snapshot으로 과거 기록 보존.
42. Analytics 이벤트 명세는 초기부터 정의, 실제 도구 연동은 SHOULD.
43. 외부 의존 기능은 Feature Flag로 운영 가능하게 한다.
44. MVP는 졸업작품 규모로 작게 구현하되 실제 서비스·수익화 확장 시 핵심 구조를 폐기하지 않게 설계한다.
45. 최종 Primary Brand Color는 **Tomato #F0523D**이고 음식 사진이 시각적 주인공이다.

# 53. 최종 제품 정의

SaveEats는 사용자가 배달음식을 먹고 싶을 때 음식 소비 자체를 비난하거나
억제하는 서비스가 아니다.

사용자는 평소 배달앱에서 하듯 음식 사진을 보고, 가게를 찾고, 메뉴와
옵션을 고르고, 장바구니에 담고, 주문금액을 확인한다.

그리고 마지막 순간에 음식 대신 그 주문금액을 자신의 계좌로 보낸다.

그 결과는 단순한 "저축 성공"이 아니라:

> **"27,000원이 내 계좌로 배달됐어요."**

라는 SaveEats만의 주문 완료 경험으로 남는다.

이 경험은 내역으로 쌓이고, 필요하면 SaveEats 리뷰가 되고, 다른 사용자의
땡김도와 리뷰를 통해 다시 음식 탐색 경험으로 이어진다.

따라서 SaveEats의 최종 제품 정체성은 다음 한 문장으로 유지한다.

> **음식을 주문하듯 메뉴를 고르고 주문한다. 다만 음식 대신 주문금액이 내
> 계좌로 배달된다.**

# 54. 인증 정책

게스트는 홈, 검색, 카테고리, 가게/메뉴 상세, 장바구니까지 사용할 수 있다. 찜, 계좌, 주문 진행, 내역, 리뷰, 마이 등 개인 행동에서 로그인한다. 로그인 성공 후 원래 행동으로 복귀한다. MVP 인증은 **이메일 + 비밀번호**를 기본으로 한다.

------------------------------------------------------------------------

# 55. 실제 서비스 확장 원칙

졸업작품 일정으로 SHOULD/LATER인 기능도 확장 경계를 막지 않는다. Seed 추천→실데이터 랭킹, Toss→정식 Transfer Provider, 단일 계좌→복수 계좌, 리뷰 이미지 1장→N장, 마스킹 이름→공개 닉네임, Seed Store/Menu→정식 데이터 Source로 발전 가능하게 한다.

상용화 전 금융 관련 법/규제·제휴, 개인정보/금융정보, 약관, 음식점 데이터·상표·이미지 사용권, 리뷰 운영정책, 수익모델을 별도 검토한다.

------------------------------------------------------------------------

# 56. Analytics 및 운영 데이터

이벤트 예: `store_viewed`, `menu_viewed`, `search_performed`, `favorite_added`, `cart_item_added`, `checkout_started`, `toss_deeplink_attempted`, `manual_transfer_selected`, `order_user_confirmed`, `review_created`, `review_helpful_clicked`. 실제 분석 도구 연동은 SHOULD.

------------------------------------------------------------------------

# 57. 성능 및 로딩 원칙

홈/검색/가게/메뉴/장바구니를 우선 관리. Skeleton/Loading State, 이미지 압축·lazy loading, 목록 점진 로딩, 부분 오류 시 정상 영역 유지. 실제 서비스 단계에서 성능 지표를 별도 정의한다.

------------------------------------------------------------------------

# 58. Feature Flag / 운영 설정

MUST: `tossDeepLinkEnabled`. SHOULD 예: `reviewEnabled`, `badgeEnabled`, `calendarEnabled`, `notificationEnabled`. MVP에서 별도 Admin UI는 필수 아님.

------------------------------------------------------------------------

# 59. 장애 우선순위와 주문 보호

가장 보호해야 하는 데이터는 **Order + 주문금액 + 목적지 계좌 Snapshot + Order Status**. 우선순위는 **송금/주문 상태 > 계좌 > 주문내역 > 리뷰 > 찜/검색/추천**. 실제 돈이 개입된 구간에서는 중복 실행보다 복구를 우선한다.
