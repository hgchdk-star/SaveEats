# 토스 이어가기 통합 실기기 확인 순서

대상: `fix/toss-integration-gaps`의 GAP-01~03 수정. 자동 테스트는 메모리 대역으로 돌린 것이라 이 표를 대신하지 않는다.
**실제 돈을 보내지 않는다.** 토스 화면의 은행·계좌·금액이 채워졌는지만 보고 최종 승인 전에 닫는다. 결과에 계좌번호·전체 딥링크·인증정보를 적지 않는다.

## 준비

- 공유 서버의 `tossDeepLinkEnabled`는 OFF가 기본이다. 켜는 일은 운영 결정이며 이 작업에 포함되지 않는다. 먼저 끄는 사람과 시간을 정한다.
- 개발 빌드 `.env`의 `EXPO_PUBLIC_TOSS_PREFILL_VERIFIED`에 시험할 `플랫폼:은행명` 조합만 넣는다. 예: `ios:토스뱅크`. 은행명은 앱의 은행 목록 표기와 같아야 한다.
- `.env`를 바꾸면 개발 서버를 다시 시작한다. 시험 기록에는 빌드 종류·기기·OS·토스 버전·은행명을 함께 남긴다 (TRF-011).

## 확인 순서

| # | 할 일 | 기대 결과 |
|---|---|---|
| 1 | 원격 ON, 등록한 조합으로 새 주문 | 첫 화면부터 은행·끝 4자리가 보이고 `토스로 주문 이어가기`가 나온다 |
| 2 | 버튼을 누른다 | 토스에 은행·계좌·금액이 채워진다. 승인하지 말고 돌아온다 |
| 3 | SaveEats로 돌아온다 | 상태 확인 뒤 `주문을 완료하셨나요?`가 나온다 |
| 4 | 이어가기 화면에 머문 채 원격을 OFF로 바꾸고 버튼을 누른다 | 토스가 열리지 않고 같은 주문의 직접 이어가기로 간다 |
| 5 | 비행기 모드로 4를 반복한다 | 3초 안에 토스 없이 직접 이어가기 또는 상태 확인 화면으로 간다. 무한 로딩이 없다 |
| 6 | 이어가기 화면에 머문 채 다른 방법으로 그 주문을 서버에서 취소한 뒤 버튼을 누른다 (직접 이어가기 화면의 취소는 PR #71 이후 가능, 토스가 열린 뒤 돌아온 질문 화면에서도 가능) | 토스가 열리지 않고 취소 화면으로 간다 |
| 7 | 등록하지 않은 은행 계좌로 주문한다 | 처음부터 직접 이어가기로 간다. 계좌번호·금액은 각각 눌러야 복사된다 |
| 8 | 주문 후 계좌를 바꾸고 내역에서 그 주문을 이어간다 | 복사·토스가 막히고 `이 기기에 주문 당시 계좌정보가 없어요.`가 나온다. 현재 계좌가 대신 나오지 않는다 |
| 9 | 주문 A에서 비행기 모드로 `주문 완료했어요`를 누른다 | 저장 실패 안내가 나오고 송금 실패라고 말하지 않는다 |
| 10 | 네트워크를 켜고 주문 B를 만든 뒤 비행기 모드로 B도 완료를 누른다 | 내역에 A·B 모두 `상태 저장 다시 시도`로 보인다 |
| 11 | 앱을 강제 종료하고 네트워크를 켠 채 다시 연다 | A·B 모두 완료로 바뀐다. 토스가 열리거나 새 주문이 생기지 않는다 |
| 12 | 9를 다시 만들고 로그아웃 후 다른 계정으로 로그인한다 | 다른 계정 내역에는 대기가 보이지 않는다. 원래 계정으로 돌아오면 복구된다 (로그아웃은 이 기기의 계좌 원문을 지운다) |
| 13 | 이전 버전 앱에서 저장 실패 상태를 만든 뒤 이 버전으로 업데이트한다 | 그 주문이 대기로 남아 있다가 복구된다 |
| 14 | 토스가 없는 기기에서 2를 시도한다 | 앱 미설치로 단정하지 않고 직접 이어가기로 간다 |

## 두 주문 동시 복구 테스트 (개발용 실패 주입)

목적: 완료 확인 대기를 A·B 두 건 동시에 남기고, 앱 재시작 한 번으로 둘 다 복구되는지 본다. 중간에 인터넷을 켜서 A만 먼저 복구되는 일을 막으려고 **네트워크를 끄지 않고** 앞의 2번 완료 확인을 개발용으로 실패시킨다.

- 서버 시작: `EXPO_PUBLIC_DEV_CONFIRM_FAILURES=2 npx expo start --tunnel --clear` (`.env`는 바꾸지 않는다. 개발 빌드에서만 동작하며 릴리스에서는 무시된다.)
- 구분: 이 실패는 **개발용 실패 주입**이다. 요청이 서버에 닿기 전에 잃은 경우를 흉내 낸 것이고, 실제 서버 오류나 응답만 잃은 경우가 아니다. 주입될 때마다 `[개발용 실패 주입]` 토스트가 뜬다. 기록에 "개발용 실패 주입"이라고 적는다. 실제 네트워크 단절 경로는 `device-test-log-20261105.md`의 T-01이 이미 확인했다.
- 주입은 사용자가 누른 `주문 완료했어요`·`상태 저장 다시 시도`만 센다. 앱 시작 복구는 건드리지 않고, 횟수는 앱을 완전히 종료하면 처음부터 다시 센다. 복구가 일어나는 시점은 앱 시작과 로그인 직후뿐이라 앱을 다시 열기 전에는 자동 복구가 없다.
- 순서: ① 주문 A → `주문 완료했어요` (토스트 1) ② 내역으로 나가 A가 `상태 저장 다시 시도`인지 본다 ③ 주문 B → `주문 완료했어요` (토스트 2) ④ 내역에서 A·B 둘 다 `상태 저장 다시 시도`인지 본다 ⑤ 앱 완전 종료 후 다시 열기 ⑥ 둘 다 `주문 완료`로 바뀌고 새 주문·토스 실행이 없어야 한다.
- 이어서(선택): 같은 방법으로 다시 A·B를 만든 뒤 ⑤ 전에 A의 `상태 저장 다시 시도`만 눌러 A만 완료되고 B는 대기로 남는지 보고, 그 뒤 앱을 재시작해 B가 복구되는지 본다. (주입 횟수 2회를 다 쓴 뒤라 이 시도는 실제 서버로 간다.)
- 자동 테스트(메모리 대역)는 같은 시나리오를 이미 통과했다. 이 수동 테스트가 대신하는 것은 실제 서버·실제 기기에서의 확인이다.

## 토스 사전입력·실행 차단 테스트 준비 (실행 전 검토 결과)

코드 검토 결과 새로 발견한 결함은 없다. 아래는 시험 전에 정해 둘 것이다. **원격 스위치와 허용 목록은 이 문서가 바꾸지 않는다.**

- 허용 목록은 `.env`가 아니라 서버 시작 명령에만 붙인다: `EXPO_PUBLIC_TOSS_PREFILL_VERIFIED='ios:토스뱅크' npx expo start --tunnel --clear`. 은행명은 앱 은행 목록 표기와 글자 그대로 같아야 한다(`토스뱅크`, `카카오뱅크`, `KB국민은행` …). 한 번에 시험할 조합 하나만 넣는다. 토스가 은행 칸을 채우지 못하면 실패로 기록하고 목록을 넓히지 않는다. 토스가 받는 `bank` 값의 표기가 앱 은행명과 같은지는 아직 확인된 적이 없다 (독립 PoC에 은행명이 기록되지 않았다).
- 빌드: iPhone의 Expo Go(독립 PoC와 같은 방식). SaveEats 자체 개발 빌드가 아니다. 이 결과를 SaveEats 릴리스 빌드의 검증으로 확대하지 않는다. 토스는 계정 본인의 은행·계좌로 시험하고 최종 승인 전에 닫는다.
- 1단계 — 공유 서버 변경 없음 (권장 먼저): 데이터를 앱 안 가짜 데이터로 돌린다. `EXPO_PUBLIC_DATA_SOURCE=mock EXPO_PUBLIC_TOSS_PREFILL_VERIFIED='ios:토스뱅크' npx expo start --tunnel --clear`. 원격 스위치는 가짜 설정(기본 ON)이고 계좌 원문은 이 기기 보안 저장소를 쓰는 실제 경로다. 토스 실행·사전입력·복귀 후 질문 화면·**취소 화면 진입**을 시험할 수 있다. 실서버의 PENDING 저장과 원격 OFF는 시험하지 못한다. 시나리오 `EXPO_PUBLIC_MOCK_SCENARIO=killSwitch`로 시작하면 처음부터 OFF(직접 이어가기)를 볼 수 있지만 화면에 머문 채 ON→OFF는 만들 수 없다.
- 2단계 — 실서버 ON→OFF (사용자가 명시적으로 요청하기 전에는 하지 않는다): 공유 개발 DB의 `public.feature_config`의 `tossDeepLinkEnabled`를 true로 바꿔야 한다. 앱 권한으로는 쓸 수 없고 DB 운영 권한(혜지)이 필요하다. 영향: ① 같은 프로젝트의 모든 클라이언트가 읽는 공개 설정이 true가 된다. ② 실제로 토스가 열리려면 해당 클라이언트가 허용 목록 조합도 갖고 있어야 해서, 위처럼 환경 값을 직접 넣은 개발 빌드만 영향을 받는다. ③ `configRevision`이 오른다(되돌려도 내려가지 않는다). 원복: 같은 행을 false로 되돌린다(`update public.feature_config set boolean_value = false where key = 'tossDeepLinkEnabled';`). 시험이 끝나면 즉시 원복하고 `get_public_feature_config`가 false로 응답하는지 확인한다. 진행 전 지우·혜지에게 알린다.
- 시험 항목은 위 14단계 표의 1~8번이다. 취소 상태 차단(6번)은 1단계(mock 모드)에서 토스를 열었다 돌아온 질문 화면에서 취소해 만든다.

## 알려진 문제

1. **(해결, 서정 확정 2026-11-06) 직접 이어가기에서 주문 취소 화면에 도달할 수 없던 문제.** 직접 이어가기 화면에도 `주문 취소` 보조 텍스트 버튼과 확인 시트를 넣었다(PR #71). 완료 확인 저장 중·저장 실패일 때는 숨기고, 취소 확인이 실패하면(CANCEL_UNKNOWN) 질문 화면과 같은 안내와 다시 확인을 보여준다. 화면 확인은 지우가 서버 연결 모드에서 했다(자동 테스트 44개에는 이 화면이 없다).
2. **(알려진 제한으로 유지, 서정 확정 2026-11-06) 해석할 수 없는 예전 형식(v2) 완료 확인 기록이 있으면 그 사용자의 이어가기·토스·복구가 계속 막힌다.** 어느 주문의 기록인지 알 수 없어 안전하게 막는 설계(재송금 유도 방지)이고, 기록은 지우지 않는다. 막힘에서 빠져나오는 방법은 아직 없다. 일반 사용에서는 거의 생기지 않는 저장소 손상일 때만 발생한다. 지금은 바꾸지 않고, 정식 배포 전에 다시 본다(선택지: 격리 후 안내 / 사용자 확인 뒤 지우기). 자동 테스트에 현재 동작을 고정해 두었다.
